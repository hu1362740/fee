# 常见问题与开发注意事项

> 本文件汇总了深度阅读代码后发现的坑点、已知问题及开发建议，供后续维护和改写参考。

---

## 一、已知代码问题 / 待改进点

### 1. `parseNginxLog.js` 流式读取未 await

**文件：** `server/src/commands/save_log/parseNginxLog.js`

**问题：** `execute()` 方法中 `readLine(...).go(...)` 没有用 `return new Promise(...)` 包裹返回，导致 `execute()` 在文件读取完成前就 `return` 了，后续的 `autoCloseOldStream` 可能未等待数据完全处理就关流。

代码中有被注释掉的正确 Promise 写法（第 155-173 行），已被注释掉，改为直接调用流式读取（无 await）。

**影响：** 在 TaskManager 调度时，SaveLog 命令可能提前结束，日志可能未完全落地就被认为执行完毕。

**修复建议：** 恢复被注释的 Promise 包裹写法。

---

### 2. Token 安全性

**文件：** `server/src/library/auth/index.js`

**问题：** `MD5_SALT = '1111111111111111111111111111'` 为硬编码固定值，生产环境极不安全。

**修复建议：** 通过环境变量或配置文件注入，例如 `process.env.TOKEN_SALT`。

---

### 3. 用户密码 MD5 SALT 硬编码

**文件：** `server/src/model/project/user.js`

**问题：** `MD5_SALT = '12345678901234567890123'` 硬编码，生产环境应修改。

---

### 4. `Task:Manager` 依赖 `ps` 命令（Linux Only）

**文件：** `server/src/commands/task/manage.js`

**问题：** `closeOtherTaskManager()` 使用 `ps aS|grep Task:Manager|...` 检测并 kill 重复进程，**此命令在 Windows 上不可用**。

**Windows 开发时**：Task:Manager 会因找不到命令而跳过进程检测，不影响功能，但无法防重。

---

### 5. `replaceInto` 非原子操作

**文件：** `server/src/model/parse/common.js`

**问题：** `replaceInto` 先 `SELECT id` 再 `UPDATE/INSERT`，高并发下可能出现竞态条件（race condition）。

**影响：** 数据量低时（私有化部署场景）一般不会有问题。

---

### 6. Nginx 日志路径配置（Windows 开发）

**文件：** `server/src/configs/common.js`

```js
nginxLogFilePath: 'D:/phpstudy_pro/Extensions/Nginx1.15.11/logs/'
```

这是一个 Windows 本地开发路径，不同机器需要修改此配置。

`parseNginxLog.js` 已做兼容处理，支持三种日志文件模式：
1. `fee-access.log`（Windows 开发）
2. `access.log`（标准 Nginx）
3. `YYYYMM/DD/HH/mm.log`（Linux 生产）

---

### 7. `base.js` 中大量注释代码

`commands/base.js` 有大量说明性注释（包括 JSDoc 风格注释），是已经修改过的文件，注释内容与原始简洁版本差别较大，阅读时要注意区分注释和实际代码。

## 二、开发常用命令速查

### Server 命令

```bash
# 启动
npm run watch    # babel 编译监听
npm run dev      # 启动 dev 服务器（NODE_ENV=development）

# 任务调度
npm run fee Task:Manager

# 手动解析日志（指定时间范围）
npm run fee Parse:Monitor '2024-01-01 10:00' '2024-01-01 10:05'

# 手动汇总数据
npm run fee Summary:UV '2024-01-01' day
npm run fee Summary:Error '2024-01-01 10' hour

# 生成建表 SQL
node dist/fee.js "Utils:GenerateSQL" "1,2" "2024-01" "2024-12" | Out-File -FilePath "init.sql" -Encoding utf8

# 写入样例数据
npm run fee Utils:TemplateSQL

# 清理旧日志
npm run fee Utils:CleanOldLog
```

### Client 命令

```bash
npm run dev      # 启动前端开发服务器（PORT 8080）
npm run build    # 构建生产包（输出到 server/public/）
```

## 三、新增项目接入流程

1. 在 `commands/utils/generate_sql.js` 中添加项目信息（id、抽样率、display_name、project_name）
2. 重新生成 SQL 并执行（只需新项目对应的部分）
3. 在 SDK 中设置对应的 `pid`（即 `project_name`）
4. 系统即可开始接收该项目的打点数据

---

## 四、抽样率说明

`t_o_project.rate` 字段，取值范围 1-10000：
- `10000` = 100%（全量收集）
- `1000` = 10%（每 10 条收 1 条）
- 日 PV 超过 10w 的项目建议降低采样率，保证每日入库不超过 10w 条

**判断逻辑（`parseNginxLog.js`）：**
```js
let checkFlag = Math.floor(logCounter % 10000)
let skipIt = checkFlag > projectRate  // checkFlag > rate 则跳过
```

## 六、登录类型切换

**文件：** `server/src/configs/common.js`

```js
loginType: 'normal'  // 普通账号密码登录
```

## 九、代码修改时的注意点

1. **修改 `server/src/` 下的文件后**，必须重新 `npm run build`（或确保 `npm run watch` 在运行），因为实际执行的是 `dist/` 目录下的编译结果。

2. **新增命令**时，必须在 `server/src/fee.js` 的 `registedCommandList` 中注册，否则命令无法被 `ace` 识别。

3. **新增 API 路由**时，必须在 `routes/api/index.js` 中 spread 引入，并通过 `RouterConfigBuilder.routerConfigBuilder()` 声明，系统会自动根据 `needLogin` / `needProjectPriv` 分配到对应路由分组。

4. **所有数据库操作**建议使用 `model/parse/common.js` 中的 `replaceInto` / `insertInto` / `updateInto`，避免直接写原始 Knex 查询，保持分表逻辑一致。

5. **ParseBase 子类**必须实现 4 个方法：`isLegalRecord`、`processRecordAndCacheInProjectMap`、`save2DB`、`getRecordCountInProjectMap`，漏实现会调用 `mustBeOverride()` 直接 `process.exit(0)`。
