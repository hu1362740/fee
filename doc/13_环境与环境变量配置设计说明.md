# 环境与环境变量配置设计说明

> 阅读范围：`server/src/configs/*`、`server/package.json`、`server/bin/run.sh`、`server/pm2_fee_app.json`、`server/pm2_fee_task_manager.json`、`client/config/*`、`client/script/*`、`client/vue.config.js`、`client/src/libs/axios.js`、`sdk/config/index.js`、`sdk/src/index.js`。
>
> 本文分两部分：第一部分说明本项目现有环境设计与配置方式；第二部分说明主流公司自用前端监控系统通常如何设计开发、测试、正式环境及环境变量。

## 一、先说结论

本项目的环境设计以 `NODE_ENV` 为核心，后端通过 `server/src/configs/env.js` 读取：

```js
let env = process.env.NODE_ENV || 'development'
```

也就是说：

- 未设置 `NODE_ENV` 时，默认走 `development`。
- `NODE_ENV=development` 走开发环境配置。
- `NODE_ENV=testing` 走测试环境配置。
- `NODE_ENV=production` 走正式环境配置。

后端各配置文件基本都采用同一种模式：

```js
const development = { ... }
const testing = { ... }
const production = { ... }

const config = {
  development,
  testing,
  production
}

export default config[env]
```

前端管理后台的情况稍微复杂一些：

- 开发服务通过 `client/config/index.js` 和 `client/script/dev-server.js` 控制端口、代理地址。
- 前端接口请求基础地址在 `client/config/url.js`。
- `npm run build` 会强制设置 `process.env.NODE_ENV = 'production'`，因此构建产物默认按生产模式打包。
- 生产构建后，前端通常与后端同域部署，接口走相对路径 `/api` 或 `/project/:id/api`。

SDK 的情况又不同：

- SDK 构建只区分开发/生产构建。
- SDK 打点上报地址由业务接入方通过 `dt.set({ reportUrl })` 在运行时配置，未配置时不会发送请求。
- SDK 是否是测试数据，主要由业务接入时传入的 `dt.set({ is_test: true })` 控制。

## 二、本项目后端环境设计

### 1. 环境入口：`server/src/configs/env.js`

后端所有环境配置的入口是：

```text
server/src/configs/env.js
```

核心逻辑：

```js
let env = process.env.NODE_ENV || 'development'
export default env
```

这意味着后端不直接读取 `.env` 文件，也没有使用 `dotenv`。环境值来自启动命令或 PM2 配置。

### 2. 启动命令如何注入环境

后端常用命令在 `server/package.json`：

```json
{
  "scripts": {
    "dev": "cross-env NODE_ENV=development nodemon dist/app.js",
    "fee": "cross-env NODE_ENV=development node dist/fee.js",
    "test_start": "NODE_ENV=testing node dist/app.js",
    "test_fee": "NODE_ENV=testing node dist/fee.js",
    "prod_start": "NODE_ENV=production node dist/app.js",
    "prod_fee": "NODE_ENV=production node dist/fee.js"
  }
}
```

含义：

| 命令 | 实际环境 | 作用 |
| --- | --- | --- |
| `npm run dev` | `development` | 启动 Express Web 服务 |
| `npm run fee ...` | `development` | 执行 CLI 命令，例如任务调度 |
| `npm run test_start` | `testing` | 以测试环境启动 Web 服务 |
| `npm run test_fee` | `testing` | 以测试环境执行 CLI |
| `npm run prod_start` | `production` | 以正式环境启动 Web 服务 |
| `npm run prod_fee` | `production` | 以正式环境执行 CLI |

注意：Windows PowerShell 下，`NODE_ENV=testing node ...` 这类写法不可用，应使用 `cross-env`、`npm run dev_test` 风格，或手动设置：

```powershell
$env:NODE_ENV='testing'
node dist/app.js
```

### 3. PM2 如何注入环境

PM2 配置在：

```text
server/pm2_fee_app.json
server/pm2_fee_task_manager.json
```

典型结构：

```json
{
  "env": {
    "NODE_ENV": "development"
  },
  "env_testing": {
    "NODE_ENV": "testing"
  },
  "env_production": {
    "NODE_ENV": "production"
  }
}
```

启动方式：

```bash
cd server
npm run build

pm2 start pm2_fee_app.json --env testing
pm2 start pm2_fee_task_manager.json --env testing

pm2 start pm2_fee_app.json --env production
pm2 start pm2_fee_task_manager.json --env production
```

解释：

- `pm2 start xxx.json` 不带 `--env` 时使用 `env`，也就是 `development`。
- `--env testing` 会读取 `env_testing`。
- `--env production` 会读取 `env_production`。
- 如果修改了环境变量后重启，建议使用 `pm2 restart fee-app --update-env`。

### 4. `server/bin/run.sh`

`server/bin/run.sh` 也支持传入环境：

```bash
./bin/run.sh start production
./bin/run.sh run testing
```

脚本中：

```bash
PROJECT_ENV=$2 # development | testing | production

if [[ -z $PROJECT_ENV ]]; then
  PROJECT_ENV=production
fi

NODE_ENV=${PROJECT_ENV} node ${PROC_NAME}
```

如果第二个参数为空，默认使用 `production`。

## 三、本项目后端各配置文件怎么配

### 1. 应用端口和日志路径：`server/src/configs/app.js`

配置项包括：

| 配置项 | 作用 |
| --- | --- |
| `name` | 应用名称，日志和启动提示中使用 |
| `port` | Express 监听端口，当前默认 `3000` |
| `proxy` | 历史字段，目前主流程未明显使用 |
| `absoluteLogPath` | 服务端日志根目录，当前为 `server/log` |

示例：

```js
const development = {
  name: 'fee监控平台开发环境',
  port: 3000,
  proxy: false,
  absoluteLogPath: path.resolve(__dirname, '../../', 'log')
}

const testing = {
  name: 'fee监控平台测试环境',
  port: 3000,
  proxy: false,
  absoluteLogPath: '/data/logs/fee-pro'
}

const production = {
  name: 'fee监控平台正式环境',
  port: 3000,
  proxy: false,
  absoluteLogPath: '/data/logs/fee-pro'
}
```

### 2. MySQL：`server/src/configs/mysql.js`

当前配置：

```js
const development = {
  host: '127.0.0.1',
  port: '3306',
  user: 'root',
  password: '123456',
  database: 'platform'
}

const testing = development
const production = testing
```

这表示测试环境、正式环境目前与开发环境共用同一份配置引用。真实部署时应拆开，例如：

```js
const development = {
  host: '127.0.0.1',
  port: '3306',
  user: 'root',
  password: '123456',
  database: 'platform_dev'
}

const testing = {
  host: 'mysql.test.internal',
  port: '3306',
  user: 'fee_test',
  password: '从环境变量或密钥系统注入',
  database: 'platform_test'
}

const production = {
  host: 'mysql.prod.internal',
  port: '3306',
  user: 'fee_prod',
  password: '从环境变量或密钥系统注入',
  database: 'platform'
}
```

重要原则：

- 开发、测试、正式库必须隔离。
- 正式库账号不应给开发机器使用。
- 密码不建议硬编码在仓库中，应从环境变量、配置中心或密钥系统注入。

### 3. Redis：`server/src/configs/redis.js`

当前配置：

```js
const development = {
  host: '127.0.0.1',
  port: '6379'
}

const testing = development
const production = testing
```

真实环境建议拆开：

```js
const development = {
  host: '127.0.0.1',
  port: '6379'
}

const testing = {
  host: 'redis.test.internal',
  port: '6379'
}

const production = {
  host: 'redis.prod.internal',
  port: '6379'
}
```

Redis 在本项目里主要用于任务调度防重、报警冷却等逻辑。测试和正式环境共用 Redis 会导致任务状态、报警冷却、缓存互相污染，必须避免。

### 4. 公共开关：`server/src/configs/common.js`

当前配置：

```js
const development = {
  loginType: 'normal',
  use: {
    kafka: false,
    alarm: false
  },
  nginxLogFilePath: 'D:/phpstudy_pro/Extensions/Nginx1.15.11/logs/'
}

const testing = development
const production = testing
```

配置项说明：

| 配置项 | 作用 |
| --- | --- |
| `loginType` | 登录方式，`normal` 为本地账号密码，`uc` 为企业 UC 登录 |
| `use.kafka` | 日志链路是否使用 Kafka |
| `use.alarm` | 是否启用报警发送 |
| `nginxLogFilePath` | 不使用 Kafka 时，读取 Nginx 日志的根目录 |

典型配置：

```js
const development = {
  loginType: 'normal',
  use: {
    kafka: false,
    alarm: false
  },
  nginxLogFilePath: 'D:/nginx/logs/'
}

const testing = {
  loginType: 'normal',
  use: {
    kafka: false,
    alarm: true
  },
  nginxLogFilePath: '/data/nginx/logs/'
}

const production = {
  loginType: 'uc',
  use: {
    kafka: true,
    alarm: true
  },
  nginxLogFilePath: '/data/nginx/logs/'
}
```

重要提醒：

- 如果 `use.kafka=false`，必须保证 `nginxLogFilePath` 存在且日志命名格式符合解析任务预期。
- 如果 `use.kafka=true`，必须配置 Kafka，并确认保存、解析任务链路可用。
- 当前仓库 `server/src/library/utils/modules/alert.js` 中读取报警开关的路径写成了 `['ues', 'alarm']`，与这里的 `use.alarm` 不一致。该问题会导致 `alarm: false` 可能不生效，建议修复为 `['use', 'alarm']`。

### 5. Kafka：`server/src/configs/kafka.js`

当前文件基本为空：

```js
const production = {}
const testing = production
const development = testing
```

如果启用 Kafka，建议按实际客户端库需要补充 broker、topic、consumer group 等字段。例如：

```js
const testing = {
  brokers: ['kafka01.test.internal:9092'],
  topic: 'fee-log-test',
  groupId: 'fee-parser-test'
}

const production = {
  brokers: ['kafka01.prod.internal:9092', 'kafka02.prod.internal:9092'],
  topic: 'fee-log-prod',
  groupId: 'fee-parser-prod'
}
```

本项目文档中描述的数据链路是 Nginx 日志或 Kafka 二选一，具体由 `common.js` 的 `use.kafka` 控制。

### 6. 报警：`server/src/configs/alarm.js`

配置项：

| 配置项 | 作用 |
| --- | --- |
| `addr` | 报警接口地址，例如企业微信、内部通知网关 |
| `app` | 报警来源应用标识 |
| `WATCH_UCID_LIST_DEFAULT` | 默认报警接收人 |
| `WATCH_UCID_LIST_BACKEND` | 后端/任务报警接收人 |

当前 `addr` 为空，表示没有真实报警地址。若启用 `common.use.alarm=true`，必须配置真实地址，否则发送报警时会请求空 URL。

建议：

```js
const development = {
  addr: '',
  app: 'fee-dev',
  WATCH_UCID_LIST_DEFAULT: [123456],
  WATCH_UCID_LIST_BACKEND: [123456]
}

const testing = {
  addr: 'https://notify.test.internal/message',
  app: 'fee-test',
  WATCH_UCID_LIST_DEFAULT: [10001],
  WATCH_UCID_LIST_BACKEND: [10002]
}

const production = {
  addr: 'https://notify.prod.internal/message',
  app: 'fee-prod',
  WATCH_UCID_LIST_DEFAULT: [20001, 20002],
  WATCH_UCID_LIST_BACKEND: [20003]
}
```

### 7. UC 统一认证：`server/src/configs/user_center.js`

配置项：

| 配置项 | 作用 |
| --- | --- |
| `api` | UC 服务地址 |
| `appkey` | 签名密钥 |
| `appID` | 应用 ID |

只有 `common.js` 中 `loginType='uc'` 时，登录链路才依赖这份配置。

当前配置为空：

```js
const production = {
  api: '',
  appkey: '',
  appID: 123456
}
```

如果正式环境使用 UC 登录，应配置：

```js
const production = {
  api: 'https://uc.prod.internal',
  appkey: '从密钥系统注入',
  appID: 123456
}
```

重要原则：

- `appkey` 不应明文提交到仓库。
- 测试环境应接测试 UC，正式环境应接正式 UC。
- 如果本地使用 `normal` 登录，可以不配置 UC。

### 8. 开放项目：`server/src/configs/project.js`

该文件配置开放项目 ID：

```js
const OPEN_PROJECT_ID_LIST = [
  1
]
```

含义是：这些项目对所有登录用户开放，不需要用户出现在 `t_o_project_member` 中。

这不是严格意义上的环境配置，但不同环境可能需要不同开放项目。例如：

- 开发环境开放演示项目。
- 测试环境开放测试项目。
- 正式环境谨慎开放，避免数据越权。

当前文件没有按 `NODE_ENV` 区分，如果需要环境隔离，可以改造成与其他配置文件一致的 `development/testing/production` 结构。

## 四、本项目前端管理后台环境设计

### 1. 开发服务：`client/config/index.js`

`client/package.json` 中：

```json
{
  "dev": "cross-env IS_DEBUG=1 node script/dev-server.js",
  "build": "node script/build.js"
}
```

开发服务入口：

```text
client/script/dev-server.js
```

它会读取：

```text
client/config/index.js
```

关键配置：

```js
dev: {
  env: ENV_DEV,
  port: _.get(debug, ['dev', 'port'], '8080'),
  assetsSubDirectory: '.',
  assetsPublicPath: '/'
},
localServer: {
  filter: function (pathname, req) {
    return pathname.indexOf('/api/') !== -1
  },
  host: {
    target: _.get(debug, ['localServer', 'host', 'target'], 'http://localhost:3000'),
    changeOrigin: true,
    ws: true
  }
}
```

含义：

- 前端开发服务器默认端口是 `8080`。
- 命中 `/api/` 的请求会代理到 `http://localhost:3000`。
- 如果存在 `client/config/debug.js`，可以覆盖端口和代理目标。
- `IS_DEBUG=1` 时才会尝试加载 `debug.js`。

示例 `client/config/debug.js`：

```js
module.exports = {
  dev: {
    port: '8081'
  },
  localServer: {
    host: {
      target: 'http://localhost:3000'
    }
  }
}
```

这个文件适合本地个人配置，通常不建议提交。

### 2. 前端接口基础地址：`client/config/url.js`

当前配置：

```js
const DEV_URL = 'http://localhost:3000'
const MOCK_URL = ''
const PRO_URL = '/'
const URL = process.env.NODE_ENV === 'development' ? DEV_URL : PRO_URL

export default URL
```

`client/src/libs/axios.js` 使用它作为 axios `baseURL`：

```js
baseURL: `${baseURL}`
```

含义：

| 前端构建环境 | baseURL |
| --- | --- |
| `development` | `http://localhost:3000` |
| 非 `development` | `/` |

这里没有单独区分 `testing`。原因是当前 `client/script/build.js` 强制：

```js
process.env.NODE_ENV = 'production'
```

所以构建测试包和正式包都会走 `PRO_URL='/'`。这种设计依赖部署环境的域名或反向代理来区分后端：

- 测试后台页面部署到 `https://fee-test.example.com/`，同域 `/api` 指向测试后端。
- 正式后台页面部署到 `https://fee.example.com/`，同域 `/api` 指向正式后端。

如果需要前端构建期区分测试和正式，可以扩展：

```js
const DEV_URL = 'http://localhost:3000'
const TEST_URL = 'https://fee-test.example.com'
const PRO_URL = 'https://fee.example.com'

const URL_MAP = {
  development: DEV_URL,
  testing: TEST_URL,
  production: PRO_URL
}

export default URL_MAP[process.env.NODE_ENV] || DEV_URL
```

同时要修改 `client/script/build.js`，不要固定写死 `production`，而是允许外部传入：

```js
process.env.NODE_ENV = process.env.NODE_ENV || 'production'
```

然后使用：

```bash
cross-env NODE_ENV=testing node script/build.js
cross-env NODE_ENV=production node script/build.js
```

### 3. `vue.config.js` 与 `client/config/env.js`

`client/vue.config.js` 中：

```js
const env = process.env.NODE_ENV || 'development'
fs.writeFileSync(path.join(__dirname, './config/env.js'), `export default '${env}'`)
```

这表示运行 Vue CLI 相关命令时，会把当前 `NODE_ENV` 写入：

```text
client/config/env.js
```

但当前 `package.json` 的实际开发和构建脚本主要使用 `client/script/*` 下的老 webpack 配置。`vue.config.js` 更像历史迁移或 Vue CLI 辅助配置。

注意：`client/config/env.js` 会被运行命令改写，提交前应检查是否出现无关变化。

### 4. 前端构建输出

`client/script/build.js`：

- 强制设置 `NODE_ENV='production'`。
- 清空并重建 `client/dist`。
- 使用 `client/script/webpack.prod.conf.js` 打包。

`client/script/webpack.prod.conf.js`：

- 使用 `config.build.env` 注入 `process.env`。
- 输出静态资源到 `client/dist`。

项目部署时通常还会把前端构建产物放到后端静态目录，由 Express 服务：

```text
server/public
```

`server/src/app.js` 中：

```js
app.use(express.static(path.join(__dirname, '../public')))
```

因此测试和正式环境可以用同一套前端产物，通过不同域名、Nginx 或后端部署目录决定访问哪个后端。

## 五、本项目 SDK 环境设计

### 1. SDK 构建配置：`sdk/config/index.js`

当前配置：

```js
module.exports = {
  version: '1.0.40',
  build: {
    bundleAnalyzerReport: false,
    env: ENV_PRODUCTION
  },
  dev: {
    bundleAnalyzerReport: false,
    env: ENV_DEV
  }
}
```

`sdk/script/build.js` 会强制：

```js
process.env.NODE_ENV = 'production'
```

SDK 构建产物主要关注版本号、压缩、输出路径等。

### 2. SDK 上报地址：`dt.set({ reportUrl })`

SDK 不再内置固定采集域名。业务方必须在初始化时传入 `reportUrl`：

```js
dt.set({
  pid: 'project_id',
  reportUrl: 'https://fee-test.example.com/dig'
})
```

如果业务站点通过自己的网关把 `/dig` 转发到 fee-pro，也可以使用同域相对地址：

```js
dt.set({
  pid: 'project_id',
  reportUrl: '/dig'
})
```

`reportUrl` 属于 SDK 传输配置，不会写入打点数据的 `common` 字段。未配置、传入空字符串或传入非字符串值时，SDK 会输出“请设置上报地址[reportUrl]”并停止该次上报。

开发、测试、正式环境应由业务应用的构建变量或运行时配置提供不同地址，而不是重新修改和构建 SDK。例如：

```js
dt.set({
  pid: 'project_id',
  reportUrl: window.__APP_CONFIG__.FEE_REPORT_URL
})
```

### 3. SDK 测试数据标记：`is_test`

SDK 初始化支持：

```js
dt.set({
  pid: 'project_id',
  reportUrl: 'https://fee-test.example.com/dig',
  is_test: true
})
```

`is_test=true` 的意义是：

- 控制台会输出调试日志。
- 打点数据会带测试标识。
- 服务端解析时应进入测试目录或测试链路，不参与正常统计。

这和“代码运行环境”不是同一件事。一个正式域名上也可以临时打 `is_test=true`，一个测试域名也可能因为配置错误打出 `is_test=false` 的正式数据。因此 SDK 接入方要明确区分：

- `environment`：当前应用运行在哪个环境。
- `is_test`：这条监控数据是否作为测试数据处理。

cd server

## 七、本项目当前环境设计的注意点

### 1. 测试和正式配置很多是别名引用

例如：

```js
const testing = development
const production = testing
```

这种写法方便本地演示，但不适合真实多环境部署。真实部署时必须拆成独立对象。

### 2. 配置中存在明文账号密码

例如 MySQL 密码在 `mysql.js` 中明文出现。生产环境应改为：

```js
password: process.env.MYSQL_PASSWORD
```

或从密钥系统读取。

### 3. 前端没有独立 testing baseURL

当前前端只区分：

```text
development -> http://localhost:3000
非 development -> /
```

测试环境和正式环境如果需要访问不同后端，主要依赖部署域名和反向代理区分，而不是前端包里的 `baseURL` 区分。

### 4. SDK 上报地址依赖业务运行时配置

`sdk/src/index.js` 不再包含固定 `feeTarget`。业务应用必须为每个环境提供 `reportUrl`；遗漏配置时 SDK 会阻止请求，避免把数据误发到占位域名。

### 5. 报警开关读取路径疑似拼写错误

`alert.js` 读取：

```js
_.get(commonConfig, ['ues', 'alarm'], true)
```

但配置文件是：

```js
use: {
  alarm: false
}
```

建议修复为：

```js
_.get(commonConfig, ['use', 'alarm'], false)
```

同时在 `alarm.addr` 为空时跳过发送，避免空 URL 触发 axios 错误。

## 八、主流公司自用前端监控系统的环境设计

下面说的是通用成熟做法，不是本项目当前实现。

### 1. 核心原则

主流公司通常遵循这些原则：

| 原则 | 说明 |
| --- | --- |
| 环境隔离 | 开发、测试、预发、正式的数据、队列、缓存、告警互不污染 |
| 配置外置 | 密码、密钥、域名、开关不写死在代码中 |
| 一次构建，多环境部署 | 尽量同一份构建产物在测试、预发、正式逐级晋级 |
| 敏感信息只在服务端 | 浏览器包里不能包含数据库密码、消息队列密码、内部密钥 |
| 配置可校验 | 启动时校验必填环境变量，缺失则失败并给出明确错误 |
| 可审计可回滚 | 配置变更经过 CI/CD、配置中心或 GitOps，有记录可回滚 |

### 2. 常见环境分层

主流监控系统通常不只三套环境：

| 环境 | 作用 |
| --- | --- |
| `local` / `development` | 开发者本机调试 |
| `test` / `qa` | 测试人员验证功能 |
| `staging` / `pre` | 预发环境，尽量与生产一致 |
| `production` | 正式环境 |
| `sandbox` | 给业务方接入 SDK 时联调使用 |

前端监控系统尤其重视 `staging/pre`，因为监控链路包含 SDK、网关、日志、队列、清洗任务、存储、查询后台、报警，一条链路中任意一环配置错误都会影响数据可信度。

### 3. 配置来源

成熟系统通常不会只靠代码里的 `config.js`。常见配置来源如下：

| 配置来源 | 适合内容 |
| --- | --- |
| `.env.local` | 开发者本机配置，不提交 |
| `.env.test` / `.env.production` | 小团队项目的环境配置 |
| CI/CD 变量 | 构建时注入 API 地址、版本号、release |
| Kubernetes ConfigMap | 非敏感运行时配置 |
| Kubernetes Secret / Vault | 密码、token、appkey |
| 配置中心 | 动态开关、采样率、报警规则 |
| CDN runtime config | 前端页面启动时读取 `/config.js` 或 `/config.json` |

推荐优先级一般是：

```text
启动参数/环境变量 > 配置中心 > 环境配置文件 > 代码默认值
```

### 4. 前端监控系统常见变量

一个成熟前端监控系统通常会显式维护这些变量：

| 变量 | 示例 | 说明 |
| --- | --- | --- |
| `APP_ENV` | `development/testing/staging/production` | 当前应用环境 |
| `APP_NAME` | `fee-web` | 应用名 |
| `APP_ID` / `PID` | `platform-admin` | 项目 ID |
| `RELEASE` | `1.8.3+gitsha` | 版本号，用于错误聚合和 sourcemap 匹配 |
| `MONITOR_DSN` | `https://collector.example.com/dig` | SDK 上报地址 |
| `API_BASE_URL` | `https://api.example.com` | 管理后台 API 地址 |
| `SAMPLE_RATE` | `0.1` | 性能、行为或错误采样率 |
| `ENABLE_ALERT` | `true/false` | 是否启用报警 |
| `LOG_LEVEL` | `debug/info/warn/error` | 日志级别 |
| `SOURCE_MAP_UPLOAD_TOKEN` | `***` | sourcemap 上传密钥，只在 CI 使用 |
| `KAFKA_BROKERS` | `kafka01:9092` | 采集链路消息队列 |
| `MYSQL_DSN` | `mysql://...` | 存储层连接，服务端私有 |
| `REDIS_DSN` | `redis://...` | 缓存层连接，服务端私有 |

其中浏览器端只能暴露非敏感变量，例如：

```text
APP_ENV
APP_NAME
RELEASE
MONITOR_DSN
SAMPLE_RATE
```

不能暴露：

```text
MYSQL_PASSWORD
REDIS_PASSWORD
KAFKA_PASSWORD
UC_APPKEY
ALERT_WEBHOOK_SECRET
```

### 5. 前端包如何区分环境

主流有两种做法。

#### 做法 A：构建期注入

每个环境构建一份前端包：

```bash
VITE_APP_ENV=testing VITE_API_BASE_URL=https://fee-test.example.com npm run build
VITE_APP_ENV=production VITE_API_BASE_URL=https://fee.example.com npm run build
```

优点：

- 简单直接。
- 代码里可以通过 `process.env` 或 `import.meta.env` 读取。

缺点：

- 测试包和正式包不是同一个产物。
- 如果测试包验证通过，正式还要重新构建，理论上可能引入构建差异。

#### 做法 B：运行时配置

前端包固定，页面启动时加载：

```html
<script src="/runtime-config.js"></script>
```

例如：

```js
window.__APP_CONFIG__ = {
  APP_ENV: 'production',
  API_BASE_URL: 'https://fee.example.com',
  MONITOR_DSN: 'https://collector.example.com/dig',
  RELEASE: '1.8.3'
}
```

优点：

- 一次构建，多环境部署。
- 配置变更不需要重新打包。
- 更适合容器化和 CDN 部署。

缺点：

- 前端启动前必须保证配置文件可用。
- 需要处理配置文件缓存，通常要 `no-cache`。

主流公司更偏向“运行时配置 + CI 注入 release”的组合。

### 6. 监控 SDK 的环境设计

成熟 SDK 通常初始化如下：

```js
monitor.init({
  appId: 'platform-admin',
  env: 'production',
  release: '1.8.3+abc1234',
  dsn: 'https://collector.example.com/dig',
  sampleRate: 0.1,
  user: {
    id: currentUser.id
  }
})
```

重要字段解释：

- `appId`：区分项目，类似本项目 SDK 的 `pid`。
- `env`：区分开发、测试、正式。错误聚合、告警策略、看板筛选都依赖它。
- `release`：区分代码版本。没有 release，线上错误很难定位到具体发布。
- `dsn`：上报地址。测试和正式通常不同，避免测试数据污染正式数据。
- `sampleRate`：采样率。正式环境数据量大，性能和行为数据通常采样；错误数据通常全量或高采样。
- `user`：用户标识。要做脱敏，不能上传手机号、身份证、明文邮箱等敏感信息。

### 7. 数据链路如何隔离

成熟前端监控系统一般按环境隔离整条链路：

```text
SDK
  -> collector
  -> gateway / nginx
  -> Kafka topic
  -> parser / consumer
  -> MySQL / ClickHouse / Elasticsearch
  -> admin UI
  -> alert system
```

隔离方式有两种：

#### 物理隔离

不同环境使用不同资源：

```text
fee-log-test topic
fee-log-prod topic

platform_test database
platform_prod database
```

优点是安全，不容易互相污染。正式环境推荐。

#### 逻辑隔离

同一套资源中增加 `env` 字段：

```json
{
  "env": "testing",
  "appId": "platform-admin",
  "release": "1.8.3",
  "type": "error"
}
```

优点是成本低，适合开发和小规模测试。缺点是一旦查询、清洗、报警漏了 `env` 条件，就可能污染数据。

成熟公司常用组合：

- 开发/测试可以逻辑隔离。
- 预发/正式尽量物理隔离。
- 所有日志仍带 `env` 字段，方便二次筛选和审计。

### 8. 报警如何按环境设计

监控系统的报警必须区分环境：

| 环境 | 报警策略 |
| --- | --- |
| 开发 | 默认不报警，只打日志 |
| 测试 | 可以报警到测试群或负责人 |
| 预发 | 可以报警，但标明 `[预发]` |
| 正式 | 报警到值班群、IM、电话或工单系统 |

报警消息里应该包含：

```text
环境：production
项目：platform-admin
版本：1.8.3
错误：TypeError xxx
影响用户数：123
首次发生时间：...
最近发生次数：...
链接：监控后台详情页
```

不能让测试环境报警混入正式告警群，否则会造成告警疲劳。

### 9. sourcemap 与 release

主流前端监控系统会把 `release` 和 sourcemap 绑定：

```bash
RELEASE=1.8.3+$(git rev-parse --short HEAD)
npm run build
monitor-cli upload-sourcemap --release $RELEASE --env production
```

浏览器错误上报：

```json
{
  "release": "1.8.3+abc1234",
  "env": "production",
  "stack": "app.abc123.js:1:12345"
}
```

服务端拿 `release` 找对应 sourcemap，还原源码位置。

关键点：

- sourcemap 不建议公开给所有用户访问。
- sourcemap 上传 token 只能在 CI 中使用。
- 每次发布必须有唯一 release。

### 10. 配置校验

成熟系统启动时会校验环境变量：

```js
const required = [
  'NODE_ENV',
  'MYSQL_DSN',
  'REDIS_DSN',
  'MONITOR_DSN'
]

for (const key of required) {
  if (!process.env[key]) {
    throw new Error(`Missing required env: ${key}`)
  }
}
```

这样比运行一段时间后才报 `Cannot read properties of null` 更好排查。

推荐本项目后续也增加配置校验，例如：

- `NODE_ENV` 必须是 `development/testing/production` 之一。
- `use.alarm=true` 时，`alarm.addr` 必填。
- `loginType=uc` 时，`user_center.api/appkey/appID` 必填。
- `use.kafka=true` 时，Kafka 配置必填。
- MySQL、Redis 必须有 host/port/database 等关键字段。

## 九、建议本项目后续演进方向

### 1. 保留现有结构，但拆开三套配置

短期最小改动：

```js
const development = { ... }
const testing = { ... }
const production = { ... }
```

不要再写：

```js
const testing = development
const production = testing
```

### 2. 敏感信息改用环境变量

例如：

```js
const production = {
  host: process.env.MYSQL_HOST,
  port: process.env.MYSQL_PORT || '3306',
  user: process.env.MYSQL_USER,
  password: process.env.MYSQL_PASSWORD,
  database: process.env.MYSQL_DATABASE
}
```

PM2 中注入：

```json
{
  "env_production": {
    "NODE_ENV": "production",
    "MYSQL_HOST": "mysql.prod.internal",
    "MYSQL_USER": "fee_prod",
    "MYSQL_DATABASE": "platform"
  }
}
```

密码建议由系统环境、密钥文件或部署平台注入，不建议写进 PM2 JSON。

### 3. 增加配置校验模块

可以新增：

```text
server/src/configs/validate.js
```

在 `app.js` 和 `fee.js` 启动时调用。这样配置缺失能在启动阶段失败，而不是运行时才出错。

### 4. 前端支持 testing 构建或 runtime-config

如果短期不想大改，可以扩展 `client/config/url.js` 支持 `testing`。

如果希望更接近主流做法，建议引入：

```text
public/runtime-config.js
```

部署到不同环境时生成不同内容，前端包保持一致。

### 5. SDK 上报地址使用独立传输配置

当前实现把传输配置与业务公共字段分开保存：

```js
const DEFAULT_TRANSPORT_CONFIG = {
  reportUrl: ''
}

let transportConfig = _.clone(DEFAULT_TRANSPORT_CONFIG)
```

业务接入：

```js
dt.set({
  pid: 'platform-admin',
  reportUrl: 'https://fee-test.example.com/dig',
  env: 'testing',
  is_test: true
})
```

其中 `reportUrl` 只决定采集请求去向，`pid` 标识项目，`is_test` 标识测试数据，三者职责不同。

### 6. 数据中增加 `env` 字段

当前 SDK 有 `is_test`，但更推荐额外增加：

```js
env: 'development' | 'testing' | 'production'
```

原因：

- `is_test` 只能表达“是否测试数据”。
- `env` 能表达数据来自哪个运行环境。
- 看板、报警、清洗、排查都应该能按 `env` 过滤。

## 十、快速配置清单

### 开发环境

- `server/src/configs/mysql.js` 指本地 MySQL。

- 密码、密钥、token 不写在仓库里。
